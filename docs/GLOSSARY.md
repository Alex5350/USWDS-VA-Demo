# Glossary

Terms used across this repo's documentation, in plain English first, precisely second. VA and
oversight terms come first because the business reader needs them; engineering terms follow.

| Term | In plain English | Precisely |
|---|---|---|
| OIG | The Office of Inspector General: an agency's internal watchdog office, the part that audits and investigates the agency itself. This portal is a demo of a VA OIG analyst workflow. | The Department of Veterans Affairs oversight office whose analysts review VA programs and payments; the demo's workflow is modeled on prioritizing that review workload, including the Office of Data and Analytics fit described in [docs/DEMO-SCRIPT.md](DEMO-SCRIPT.md). |
| FWA | Shorthand for fraud, waste and abuse: the kinds of trouble an oversight team watches for. This demo looks for signals worth a closer look, never concludes any of the three. | Fraud, waste and abuse; the compound term behind the portal's name (VA OIG FWA Risk Triage & Reporting Portal). The product language is triage and prioritization, never "FWA detected". |
| Community Care | The VA program that pays for veterans to receive care from non-VA (community) providers when the VA cannot provide it directly. Its claims, authorizations and providers are the records this demo triages. | The VA program whose claims, authorizations, provider records, hotline complaints and cases make up the synthetic dataset; see [docs/DATA-DICTIONARY.md](DATA-DICTIONARY.md) for the schema. |
| Improper payment | Any payment that should not have been made, or was made in the wrong amount, for any reason, including honest error. Improper does not mean fraudulent. | A payment-concept term from payment-integrity work; in this demo, related indicators such as duplicate-payment candidates are review signals, not findings. |
| Questioned cost | A dollar amount an reviewer flags as possibly improper and worth checking. It is an estimate attached to a review candidate, not money anyone has been judged to owe. | Estimated questioned cost: a triage metric computed by the SQL views (`vw_DashboardSummary`, `vw_ProviderRiskSummary`, `vw_QuestionedCostByMonth`) and surfaced in reports as a prioritization indicator, never a verdict or audited finding. |
| Risk indicator vs fraud determination | An indicator is a reason to look at a record ("this claim has no matching authorization"); a determination is a conclusion that wrongdoing occurred. This product produces only the first kind. | The portal's language boundary: risk indicators with rule references and human-readable explanations surface review candidates; the application does not determine fraud, and the disclaimer appears on every page that displays data ([ADR 0003](adr/0003-synthetic-data-boundary.md)). |
| Triage | Sorting by urgency, the way an emergency room sorts patients: not diagnosing, deciding who gets attention first. The whole product is a triage tool for analyst workload. | The prioritization model: deterministic, explainable rules score records so the risk queue ranks what most deserves analyst review ([docs/SPECIFICATION.md](SPECIFICATION.md)). |
| VISN | The VA's regional health-care networks (Veterans Integrated Service Networks); roughly the VA's version of regions. Synthetic VISN values appear in the demo data. | Veterans Integrated Service Network; a region column on the synthetic `VeteranProfiles` table in [docs/DATA-DICTIONARY.md](DATA-DICTIONARY.md). |
| Section 508 | The federal law that requires government technology to be usable by people with disabilities: keyboard operation, screen reader support, readable contrast. For a VA-facing tool this is a legal floor, not a nice-to-have. | The accessibility statute this demo treats as a hard requirement; the written contract every page is held to lives in [docs/ACCESSIBILITY-508.md](ACCESSIBILITY-508.md) ([ADR 0002](adr/0002-uswds-accessibility-first.md)). |
| USWDS | The U.S. Web Design System: the federal government's official component library, so a site looks and behaves like a government site. Adopted as-is here, customized without forking. | `@uswds/uswds` 3.x imported as distributed and wrapped in our own React components and Sass layer; files inside `node_modules` are never edited ([ADR 0002](adr/0002-uswds-accessibility-first.md)). |
| Clean architecture hybrid | Organizing code in layers where dependencies point one way (inward), mixed with grouping by feature. The point: business rules can be tested and read without wading through databases and web plumbing. | Four backend projects (Api, Application, Domain, Infrastructure) with strict reference directions; Domain has zero framework dependencies; EF Core and Dapper repositories both sit behind Application-defined interfaces ([ADR 0001](adr/0001-clean-architecture-hybrid.md)). |
| Offline fallback / embedded dataset | The interface ships with a built-in copy of the (synthetic) demo data, so it works even with no server running. Like a car radio that still plays stored stations out of range. | Every client data call goes through one gateway (`api-client.ts`) with a request/fallback contract: try the API, else return an embedded typed dataset mirroring the documented DTO shapes; the risk-queue fallback applies filtering and pagination locally ([ADR 0004](adr/0004-client-offline-fallback.md)). |
| Mock authentication | Pretend sign-in for demos: pick a role from a menu instead of entering credentials. Good for showing an authorization model; never real security. | The `DemoAuth` scheme maps an `X-Demo-User` header to one of five demo users (ReadOnly through Administrator); server-side policies are enforced per endpoint while the frontend role selector is convenience UI only ([docs/SECURITY.md](SECURITY.md)). |
| Read-only AI boundary | The chat assistant may look things up and summarize, but the tools it is given cannot change anything. Like a librarian who can fetch any book but is not allowed to write in them. | The assistant's tool set is limited to bounded read endpoints (counts, case summaries, risk queue search, provider risk, case aging) over existing services; the blast radius of a bad generation is a wrong summary that cites its data ([ADR 0005](adr/0005-ai-assistant-boundary.md)). |
| SQL-backed reporting | Reports computed by the database itself, from named queries kept in files anyone can read, rather than assembled invisibly inside application code. | Dapper repositories call parameterized views and stored procedures (`database/views/`, `database/procedures/`); the same procedures back the screens, CSV exports and print output ([docs/REPORTING.md](REPORTING.md)). |
| EF Core / Dapper | Two ways .NET code talks to SQL Server. EF Core speaks in C# objects (used here for day-to-day writes); Dapper runs hand-written SQL (used here for reports). | Entity Framework Core for transactional data via LINQ; Dapper for read-only reporting queries kept close to the SQL views ([ADR 0001](adr/0001-clean-architecture-hybrid.md)). |
| ADR | Architecture decision record: a short memo capturing one decision, why it was made, and what it cost. This repo keeps five. | The numbered records in [docs/adr/](adr/): clean architecture hybrid, USWDS/accessibility-first, synthetic data boundary, client offline fallback, AI assistant boundary. |
